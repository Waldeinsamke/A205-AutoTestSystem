## 2. 严重级问题（H-x）详情与修复建议

### H-1. Logger 事件订阅方异常被完全吞咽
**文件**：[`Common/Logger.cs:143-156`](file:///d:/JProgram/2026/A205自动测试系统/Common/Logger.cs#L143-L156)
**现象**：
```csharp
private static void RaiseMessageLogged(string line)
{
    Action<string> handler = MessageLogged;
    if (handler != null)
    {
        try { handler(line); }
        catch
        {
            // 订阅方异常不应影响主流程
        }
    }
}
```
**风险（修正版）**：
- ✅ **文件落盘不受影响**：`WriteToFile`（[`Logger.cs:125-141`](file:///d:/JProgram/2026/A205自动测试系统/Common/Logger.cs#L125-L141)）在 `RaiseMessageLogged` 之前执行（[`Logger.cs:47-49`](file:///d:/JProgram/2026/A205自动测试系统/Common/Logger.cs#L47-L49)），所以日志**一定**会写入文件，**"整条日志都不会被记录到任何文件"是错误描述**。
- ❌ **UI 实时显示丢失**：当订阅方（如 `AutoTestPanel.OnLogMessage` / `ReceiverControlPanel.OnLogMessage`）因 TOCTOU（`IsDisposed` 检查与 `AppendText` 之间被 Dispose）、极端长字符串触发 `Text.Length` 异常、或 `ScrollToCaret` / `AppendText` 在窗口 handle 重建时抛错——UI RichTextBox 不显示这条日志。
- ❌ **无法定位**：catch 是无参 `catch`（连 `ex` 都没接收），未走 `Console.Error`，**任何位置都没有记录"是哪个订阅方抛了什么异常"**——这是核心问题。
- 注：之前描述中"订阅链断裂后其他订阅方也收不到"是 .NET `MulticastDelegate` 的**固有行为**（某 handler 抛异常，后续 handler 本就不会被调用），与本 catch 无因果关系；之前描述中"`InvokeRequired` 应同步检查"也是错的——`AutoTestPanel.cs:980-988` 与 `ReceiverControlPanel.cs:1442-1450` 已经正确用 `BeginInvoke` 异步投递并对 `BeginInvoke` 自身抛错兜底。

**实际触发路径**：
1. TOCTOU：`IsDisposed` 检查在 976/1438 行通过，紧接着 `AppendText` 在 995/1457 行执行，期间面板被 Dispose → 抛 `ObjectDisposedException`
2. `rtbLog.Text.Length` 在极端长字符串下触发内部异常
3. `ScrollToCaret` / `AppendText` 在窗口最小化或 handle 重建时抛异常

任一发生时：文件**有**这条日志；UI RichTextBox **不显示**；**无任何位置记录订阅方异常**。

**修复建议（最小改动，UI 端无需变动）**：
仅改 `Logger.cs` 的 catch 即可：
```csharp
catch (Exception ex)
{
    try
    {
        // 防止递归：直接走 Console.Error，不经过 Logger 自身
        Console.Error.WriteLine(
            $"[{DateTime.Now:HH:mm:ss.fff}][Logger] subscriber throw: {ex}");
    }
    catch { /* 兜底：连 Console.Error 都不可用 */ }
}
```
`UI/AutoTestPanel.cs:980-988` 与 `UI/ReceiverControlPanel.cs:1442-1450` 的 `OnLogMessage` 已正确处理 `InvokeRequired` 与 `IsDisposed`，**无需修改**。

**风险等级修正**：原"严重" → **"高"**。理由：影响范围仅限 UI 实时显示与排查能力；日志持久化不受影响；触发依赖偶发边界条件，非日常必现。

### H-2. RunSingleTestAsync 的 finally 块跨线程写 UI
**文件**：[`UI/AutoTestPanel.cs:784-826`](file:///d:/JProgram/2026/A205自动测试系统/UI/AutoTestPanel.cs#L784-L826)
**现象**：`finally` 块直接访问 `dgvTests.Rows[i].Cells[ColAction]`。该方法由 `async void` 启动，理论上 `ConfigureAwait(true)` 会回到 UI 线程，但以下场景会失控：

1. **面板已 Dispose**：行 `dgvTests.Rows.Count` 在 `finally` 中被读取时，若 `AutoTestPanel.Dispose` 已调用并 `components.Dispose()`，会抛 `ObjectDisposedException`，异常被 `.ConfigureAwait(true)` 的同步上下文吞咽，导致状态永久错乱。
2. **用户切 Tab**：当前 Tab 切换到 AutoTest 后，`dgvTests` 处于未初始化状态（虽然同实例，但 BeginInvoke 队列可能延迟到下一帧）。

**触发路径**：
1. 用户点行 ▶ 运行 → `RunSingleTestAsync` 启动 → 用户立即点 "■ 停止" 触发 `_runCts.Cancel()` → 测试项内 `ct.ThrowIfCancellationRequested` 抛出 → 进入 `finally` → 同一时刻用户切到 AutoTest Tab 或直接关闭面板 → `dgvTests` 已释放或被 Dispose → 异常。

**修复建议**：在 `finally` 开头加：
```csharp
if (IsDisposed || !IsHandleCreated) return;
// 进入 finally 时，先检查
if (dgvTests != null && !dgvTests.IsDisposed && dgvTests.IsHandleCreated)
{
    // ... 现有逻辑
}
```
并把整个 `finally` 内容用 `BeginInvoke` 包装，确保在 UI 线程上执行。

### H-9. DisconnectRf 异常路径下 _rfGenerator 未释放
**文件**：[`UI/ReceiverControlPanel.cs:596-614`](file:///d:/JProgram/2026/A205自动测试系统/UI/ReceiverControlPanel.cs#L596-L614)
**问题**：
```csharp
finally

    try { _rfGenerator?.Dispose(); } catch { }   // catch 吞咽
    _rfGenerator = null;                          // 即便 Dispose 失败仍置 null

```
如果 `Dispose()` 内部抛 `ObjectDisposedException`（驱动层罕见但发生过），`_rfGenerator` 引用被置 null 但对象本身未被释放，**下次"一键连接"不会重复 Dispose 已损坏的对象**——但 `VisaBaseInstrument._disposed = true` 已设，后续调用 `Dispose()` 会立即返回，但 `_transport` 已泄漏。
**修复**：在 `finally` 中**先**置 null 再 Dispose：
```csharp
var toDispose = _rfGenerator;

{
    try { toDispose.Dispose(); } catch (Exception ex) { Logger.Log("..."); }
}
```
