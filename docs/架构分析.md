## 一、总体结构：四层分工

代码实际呈现出**四层**结构，而非笼统的"三层"。每层职责单一，层间只通过明确的数据契约传递。

| 层 | 主要文件 | 职责 |
|---|---|---|
| **UI 层** | `UI/AutoTestPanel.cs`、`UI/MainForm.cs`、`UI/ReceiverControlPanel.cs` | 显示进度与结果、按钮态管理、把用户操作转成方法调用 |
| **业务层** | `InstrumentControl/TestItems/*.cs`（19 个测试项） | 测量流程编排：设频 → 发频段命令 → 扫频/等待 → 搜峰读值 → 判定 |
| **驱动层** | `SignalGenerator.cs`、`SignalGeneratorLO.cs`、`SpectrumAnalyzer.cs`、`ODP3063.cs`、`ReceiverSerialPort.cs` | 把业务意图翻译成 SCPI / 私有协议命令串 |
| **传输层** | `VisaBaseInstrument.cs`、`NationalInstrumentsVisaTransport.cs` | VISA 会话管理：打开资源、读写、超时、重试、失联标记 |

外加两个横切支撑模块：

- `Common/TestReportManager.cs` + `Common/ExcelExporter.cs`：结果聚合与 Excel 落盘
- `ReceiverControl/ReceiverCommandBuilder.cs`：接收机 7 字节私有协议的帧构造

## 二、分层的核心特征：下层不认识上层

这是判断分层是否成立的**唯一可靠标准**。可以用反向验证法检验：假设要改某件事，波及范围是否被限制在这一层内。

### 2.1 驱动层：只认"意图"，不认"业务"

`SignalGenerator.cs` 中的一个典型方法：

```csharp
public void SetFrequency(double freqHz)
{
    double freqMHz = freqHz / 1e6;
    SendCommand(string.Format(CultureInfo.InvariantCulture, ":FREQ {0} MHz", freqMHz));
}
```

这个方法**不知道调用方是"带内虚假信号"还是"中频带外抑制"**，也不知道 Mode1/2/3 的区别、不关心当前频段是多少。它只表达一件事：把载波频率设为 X Hz。

### 2.2 业务层：只认"意图"，不碰协议字符串

`OutOfBandRejectionTest.cs` 中 Mode3 第一段扫频的完整指令序列：

```csharp
_rf.SetFrequencyModeSweep();
_rf.SetSweepStartFrequency(Mode3RfSweep1StartHz);
_rf.SetSweepStopFrequency(Mode3RfSweep1StopHz);
_rf.SetSweepPoints(Mode3RfSweep1Points);
_rf.SetContinuousSweep(true);
```

这段代码里**找不到任何一个 `:FREQ:STAR` 之类的原始 SCPI 字符串**。业务层表达的是"进入扫频、设起点、设终点、设点数、启动"五个动作。

带来的直接收益：若某台仪器的扫频点数命令需要从 `:SWE:POIN` 改为其它形式，只需修改 `SignalGenerator.SetSweepPoints` 一处，全部测试项无需改动。

### 2.3 UI 层：只认"结果"，不碰仪表

`AutoTestPanel.cs` 中执行测试项的核心片段：

```csharp
TestResult result = await test.ExecuteAsync(progress, _runCts.Token)
                                  .ConfigureAwait(true);
statusCell.Value = string.Format(CultureInfo.InvariantCulture,
    "{0} ({1:F2} {2})", result.Judgment, result.Value, result.Unit);
```

UI 层拿到 `TestResult` 对象后只读三个字段用于显示。它**不关心** `-35.21 dBm` 这个数字是RF 扫频测出来的、还是一中频抑制测出来的。

## 三、层间传递：三个方向，三种契约

### 3.1 UI → 业务层：接口

`AutoTestPanel` 持有的类型是 `ITestItem`，而非任何具体测试类：

```csharp
public interface ITestItem
{
    string TestName { get; }
    string Unit { get; }
    double? LowerLimit { get; }
    double? UpperLimit { get; }
    Task<TestResult> ExecuteAsync(IProgress<string> progress, CancellationToken ct);
}
```

**收益**：新增测试项时 UI 层完全不需要改动——只要新类实现该接口，`TestCatalog` 里加一行就能出现在界面上。

### 3.2 业务层 → 驱动层：构造函数注入

```csharp
public OutOfBandRejectionTest(
    ReceiverSerialPort receiver,
    SignalGenerator rfGenerator,
    SignalGeneratorLO loGenerator,
    SpectrumAnalyzer spectrumAnalyzer,
    int channel,
    IReadOnlyList<ReceiverMode> modes = null,
    IReadOnlyDictionary<ReceiverMode, double[]> testFreqsMHzPerMode = null)
```

仪表实例由外部创建后传入，测试项**从不自己 `new`**。

`TestCatalog` 在这里扮演**组装根（Composition Root）**的角色——它是唯一知道真实仪表 VISA 地址的地方：

```csharp
new OutOfBandRejectionTest(
    receiver: receiver, rfGenerator: rf, loGenerator: lo,
    spectrumAnalyzer: sa, channel: channel, modes: allModes),
```

同一个 `rf` / `lo` / `sa` 实例被连续传给 19 个测试项，**保证一台物理仪器只被一个会话驱动**。

构造函数内含防御性校验：

```csharp
if (rfGenerator == null) throw new ArgumentNullException(nameof(rfGenerator));
```

漏传依赖会在**构造时立即失败**，而不是等到运行时变成难以定位的 `NullReferenceException`。

### 3.3 业务层 → UI 层：强类型结果对象

```csharp
public class TestResult
{
    public DateTime TestTime { get; set; }
    public string TemperatureRange { get; set; }
    public int Channel { get; set; }
    public string Mode { get; set; }
    public string TestItem { get; set; }
    public int? BandIndex { get; set; }
    public string BandDisplayName { get; set; }
    public double Value { get; set; }
    public string Unit { get; set; }
    public string Judgment { get; set; }
    public string Remarks { get; set; }
}
```

**收益**：全流程用强类型传递，避免了字符串管道中常见的"某个环节漏解析/漏处理导致静默错误"。`BandIndex` 刻意声明为 `int?`，用`null` 表达"本条结果与频段无关"（如带宽测试），而不是用 `-1` 这类魔法值。

## 四、传输层的额外抽象：IVisaTransport

驱动层之上还有一层值得关注的设计——`IVisaTransport` 接口把"VISA 驱动"本身也抽象掉了：

```csharp
public interface IVisaTransport : IDisposable
{
    string Address { get; }
    bool IsOpen { get; }
    int TimeoutMilliseconds { get; set; }
    void Open();
    void Write(string data);
    string ReadString();
}
```

**两套实现**：

| 实现 | 位置 | 用途 |
|---|---|---|
| `NationalInstrumentsVisaTransport` | 生产代码 | 真实 NI VISA 25.0 |
| `FakeVisaInstrument` | `Tests/*/FakeVisaInstrument.cs` | 单元测试替身 |

`VisaBaseInstrument` 只依赖接口，不直接引用 `NationalInstruments.Visa` 的类型。测试时通过 `SetTransport()` 注入伪传输：

```csharp
protected void SetTransport(IVisaTransport transport)
```

这使得**整个仪表调用链可以在没有硬件的环境下测试**。`Tests/AutoTest.Tests` 正是靠这一点，用 `<Compile Include>` 直接链接生产源码进行验证。

## 五、值得称道的具体细节

以下都是代码中实际存在的、并非泛泛而谈的优点。

### 5.1 硬件测试的异常路径被系统性兜住

硬件测试最大的风险是**异常路径下仪表状态失控**（信号源一直开着、扫频一直跑着），会污染后续所有测试项。项目对此有系统处理：

```csharp
finally
{
    try { _rf.ExitSweep(); } catch { /* best-effort */ }
    try { _rf.SetOutputState(false); } catch { /* best-effort */ }
    try { _lo.SetOutputState(false); } catch { /* best-effort */ }
    Logger.Log("[OutOfBandRejectionTest] RF/LO 输出已关闭（finally）。");
}
```

**关键在于每条命令单独 `try`**。如果写成一个大 `try`，第二条抛异常会导致第三条不执行，信号源会一直保持开启。

`ExitSweep()` 内部把"停扫描 + 切回 CW"两条命令固化为一个语义，避免测试项各自拼 `:INIT:CONT 0` 而漏掉模式复位（见 6.1）。

### 5.2 瞬态错误重试 + 非瞬态错误立即标记失联

`VisaBaseInstrument.ExecuteWithRetry` 对错误做了分类处理：

```csharp
catch (VisaException vex) when (IsTransientError(vex))
{
    // 超时 / 系统错误 / IO / 连接丢失 → 指数退避重试
    int delayMs = (int)(100 * Math.Pow(2, attempt - 1));
    Thread.Sleep(delayMs);
}
catch (Exception ex)
{
    // 非瞬态 → 立即标记失联并抛出
    MarkInstrumentLost(ex, "non-transient exception");
    throw;
}
```

`IsTransientError` 通过 VISA规范的 `HResult` 常量判定（`VI_ERROR_TMO = -1073807339` 等）。

`MarkInstrumentLost` 会把 `IsConnected` 置false、释放 transport、触发 `ConnectionChanged(false)` 事件让 UI 状态灯变红。代码注释解释了这样做的原因：

> 避免线缆掉了但 IsConnected 字段还卡 true、导致「一键连接」走"已连接"快路径跳过重连，直到下次发命令才报错。

### 5.3 解析失败时错误信息自带定位线索

`SpectrumAnalyzer.ParseMarkerY` 统一处理异常响应：

```csharp
private double ParseMarkerY(string scpi)
{
    string resp = QueryString(scpi);
    if (string.IsNullOrWhiteSpace(resp))
        throw new InvalidOperationException(
            $"频谱仪 Marker Y? 返回空响应（命令：{scpi.TrimEnd('\n')}）。" +
            "请检查仪表连接与状态，或确认测试桩是否预设了对应命令的响应。");
    if (!double.TryParse(resp, NumberStyles.Float, CultureInfo.InvariantCulture, out double value))
        throw new InvalidOperationException(
            $"频谱仪 Marker Y? 响应无法解析为数值：'{resp}'（命令：{scpi.TrimEnd('\n')}）。");
    return value;
}
```

这比直接 `double.Parse(resp)` 强得多——后者抛出的 `FormatException` 不包含"是哪台仪表、哪条命令"，排查时需要顺着调用栈反推。异常消息中直接嵌入 SCPI 命令原文，定位成本大幅降低。

### 5.4 时序常量全部具名且写明依据

```csharp
// Mode3 RF 真的在扫频（10~1660 / 2340~2650 MHz），需 10s 让 MAXH 累积到稳态；
// Mode1/2 RF 不扫频，只需要等待频谱仪完成一次 sweep + 短稳态，
// 3500 MHz span + 100 kHz RBW 在 PXA 上 sweep 通常 ~50ms~几百 ms，给 2s 保险。
private const int Mode3SweepWaitMs = 10_000;
private const int Mode12SweepWaitMs = 2_000;
```

注释不是"等一下"，而是**解释为什么是这个量级**。三个月后调整该值的人能判断依据是否依然成立。这比单纯给常量命名值钱得多。

### 5.5 文化差异在协议边界处被显式处理

```csharp
SendCommand(string.Format(CultureInfo.InvariantCulture, ":FREQ {0} MHz", freqMHz));
```

所有 SCPI 字符串格式化都显式指定 `InvariantCulture`。原因：若在某些区域设置下小数点变成逗号，`:FREQ 1234,5 MHz` 会被仪表解析成非法格式。这类问题在中文Windows 上通常不出现，但一旦部署环境变化就是灾难性且难以定位的。

### 5.6 报表聚合考虑到了并发

`TestReportManager` 采用 `Lazy<T>` 线程安全单例，且所有公共方法用 `lock` 串行化：

```csharp
private static readonly Lazy<TestReportManager> _instance =
    new Lazy<TestReportManager>(() => new TestReportManager(), isThreadSafe: true);
```

原因写在类注释里：WinForms 异步测试项可能并发调用导致行乱序。测试项在 `ExecuteAsync` 内直接 `Record`，UI 在用户点击"导出"时才落盘——生产者/消费者职责清晰。

## 六、当前已知的架构边界模糊点

分层的"干净"不是自动达成的。以下问题在本次优化中被实际观察到，值得记录：

### 6.1 退出扫频的方式在测试项间不一致 ✅ 已解决

**问题描述（已修复）**：修复前退出扫频的写法在各测试项间不一致——

- `BandwidthTest` 退出扫频只发 `:INIT:CONT 0`
- `OutOfBandRejectionTest` 同样只发 `:INIT:CONT 0`
- 只有 `InBandSpuriousTest` 额外发了 `:FREQ:MODE CW`

这是**协议层知识以业务代码形式散落在多个测试项**的典型信号：真出问题需要逐个排查，而非改一处即可。

**关键认知**：`:INIT:CONT 0` 只停扫描触发，**频率模式仍是 SWE**。后续测试项只发 `:FREQ` 而不改 `:FREQ:MODE`，载波会继续按扫频走，读到的 IF 峰值是错的——而且不报错，属静默错误。该隐患影响整条测试链（`GainTest`、`InputP1Test`、谐波等测试项在此之前都只发 `:FREQ` 就直接读数），不只带内虚假信号一项。

**解决方案**：在 `SignalGenerator` 增加 `ExitSweep()`，把"停扫描 + 切回 CW"固化为驱动层的一个完整语义：

```csharp
public void ExitSweep()
{
    SendCommand(":INIT:CONT 0");
    SendCommand(":FREQ:MODE CW");
}
```

`BandwidthTest`（finally 收尾）、`OutOfBandRejectionTest`（finally 收尾 + Mode3 段间切换 ×2）、`InBandSpuriousTest`（逐频点收尾）现统一调用该方法。段间调用同样安全：下一段扫频会重新发 `:FREQ:MODE SWE` 切回扫频模式。

> **现场待验证**：`:INIT:CONT 0` 是否会隐式把频率模式切回 CW，仍需在真实信号源上实测确认。当前实现按"不会隐式切换"的保守假设处理，即显式补发 `:FREQ:MODE CW`——多发一条命令无副作用，漏发则会造成静默错误。
> **回归防护**：`Instrument.Tests` 新增 `TestSweepExit`，断言 `ExitSweep()` 恰好发两条命令且顺序为"先停扫描、后切 CW"，并覆盖"进扫频→退出→再进扫频"的完整生命周期。

### 6.2 UI 层的注释与代码曾长期不一致

`AutoTestPanel` 中的 `cmbMode`（模式选择下拉框）从建立起就**从未被读取过**——没有任何代码使用它的 `SelectedIndex`。它在初始化时被填充、在运行中被置灰、在结束后恢复，完整走完了"看起来在工作"的假象，但实际不影响任何行为。

真实的模式选择由 `TestCatalog` 中写死的 `allModes` 决定，与该控件无关。已删除。

### 6.3 业务层中残留的协议细节

业务层里仍存在少量直接调用 `SendCommand` 的地方（如 `:CALC:MARK1:MAX:PEAK:SEARCH`）。这属于**有意的权衡**——这类命令是该测试项特有的测量动作，封装进驱动层反而不清晰。判断标准：

| 场景 | 做法 |
|---|---|
| 高频使用、有单位换算或格式讲究 | 应封装到驱动层 |
| 测试项特有的专用测量动作 | 可直接 `SendCommand` |

## 七、架构收益汇总

| 收益点 | 具体体现 |
|---|---|
| **协议变更隔离** | 换仪表型号只需改驱动层，19 个测试项不动 |
| **可测试性** | `IVisaTransport` 抽象使整个调用链可在无硬件环境下测试 |
| **并发安全** | 仪表失联即时上报、报表写入串行化、重试机制分层 |
| **故障定位** | 异常消息内嵌 SCPI 命令原文与仪表类型 |
| **知识沉淀** | 时序常量注释写明量化依据，参数可调且可追溯 |
| **单一职责** | 单个测试项类只负责一个指标，可独立阅读、独立删除 |
| **资源高效** | 19 个测试项共享同一组仪表实例，一台物理仪器一个会话 |

## 八、后续演进建议

以下为可选优化，非当前缺陷：

1. **抽取"分段测量"公共逻辑**
   当前 `OutOfBandRejectionTest` 的 Mode3 两段扫频与 Mode1/2 两段扫描骨架高度相似（设窗口 → 等稳定 → 搜峰 → 读值），仅参数不同。若后续需增加模式或频段，可考虑抽取私有方法 `MeasureSegmentAsync(windowStart, windowStop, waitMs, useMaxHold)`，让差异收在一处。

2. **统一退出扫频语义** ✅ 已完成
   见 6.1。`SignalGenerator.ExitSweep()` 已实现（发 `:INIT:CONT 0` + `:FREQ:MODE CW`），三个扫频类测试项统一调用，并已补 `Instrument.Tests` 回归测试。

3. **测试参数配置化**
   当前所有测试参数均为 `const`，编译期固化。若未来需要操作者在界面上调整扫频范围、等待时长等，需改为可配置形式（配置文件加载或 `static` 字段）。这属于配置管理范畴，与依赖注入是两个独立议题。
