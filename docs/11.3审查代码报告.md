## 2. 🔴 严重级问题

### #1 ⬆️ 增益不一致性汇总行仍只看极差，完全忽略规格区间

**位置**：[AutoTest/Shared/GainConsistencyCalculator.cs:74-101](file:///d:/JProgram/2026/A205自动测试系统/AutoTest/Shared/GainConsistencyCalculator.cs#L74-L101)、[ChannelGainInconsistencyTest.cs:254](file:///d:/JProgram/2026/A205自动测试系统/InstrumentControl/TestItems/ChannelGainInconsistencyTest.cs#L254)、[ChannelGainInconsistencyAgcOnTest.cs:331](file:///d:/JProgram/2026/A205自动测试系统/InstrumentControl/TestItems/ChannelGainInconsistencyAgcOnTest.cs#L331)

**问题**：

`Compare` 计算 `Range = gains.Max() - gains.Min()`，判定直接使用 `comparison.RangePass`（即 `Range <= 1.0 dB`）。规格区间定义在 [GainTest.cs:58-60](file:///d:/JProgram/2026/A205自动测试系统/InstrumentControl/TestItems/GainTest.cs#L58-L60)：

```csharp
private const double Mode1Center = 20.0, Mode1Tol = 2.0;   // [18.0, 22.0]
private const double Mode2Center = 10.0, Mode2Tol = 1.0;   // [ 9.0, 11.0]
private const double Mode3Center = 20.0, Mode3Tol = 1.5;   // [18.5, 21.5]
```

**升级点**：AGC 起控项的**逐频点行**已改用 `IsInRange`（[ChannelGainInconsistencyAgcOnTest.cs:209-210](file:///d:/JProgram/2026/A205自动测试系统/InstrumentControl/TestItems/ChannelGainInconsistencyAgcOnTest.cs#L209-L210)），这是本轮的进展。但**两个测试项的汇总行判定仍只看极差**（`ChannelGainInconsistencyAgcOnTest.cs:331` 与 `ChannelGainInconsistencyTest.cs:254` 均为 `Judgment = comparison.RangePass ? "Pass" : "Fail"`），且**不起控项全文件 0 处引用 `IsInRange`**（仅 `GainConsistencyCalculator.cs:106-109` 定义处）。

**失效场景**：等效增益 25 / 21.5 / 21.6 dB —— 25 dB 超出 [18,22] 上限 3 dB，但极差仅 3.5 → 需精确构造更极端场景：25 / 21.5 / 24.9 dB 极差 3.5 > 1 会被拦。真正的失效场景是**所有频点整体超差但彼此接近**：25 / 25.2 / 25.4 dB，极差 0.4 ≤ 1 → **判定 Pass**，而三个频点全部超出上限 3 dB。

**影响**：产品增益整体偏离规格但通道间一致时，系统报"通道间一致性好 = Pass"，掩盖增益本身超差的事实。

**建议**：Pass 判定需同时满足：

1. 每个频点增益 ∈ 该模式规格区间（`IsInRange`）
2. 极差 ≤ 1 dB（`RangePass`）

建议在 `Comparison` 中新增 `AllInRange` 属性集中承载条件 1，避免在两个调用点重复实现。

> **注**：本条与 #33（判据区间不落表）叠加后，人工复核也无法从报表发现汇总行的口径错误 —— 见 §4 说明。

## 3. 🟠 中等级别问题

### #7 🔁 `AutoTestEngine.RunAllAsync` 在生产中零调用，核心调度逻辑未被测试覆盖

> **本条已于 2026-11-03 复核并修订定性。** 原文写作「形同虚设，调度逻辑双份」，经逐行比对生产循环与引擎循环后，**「双份」的说法不准确**，实际是「生产调度逻辑完全未被测试覆盖」。详见下方 §3.7 逐行比对表。

**位置**：[AutoTest/AutoTestEngine.cs:61-91](file:///d:/JProgram/2026/A205自动测试系统/AutoTest/AutoTestEngine.cs#L61-L91)、[UI/AutoTestPanel.cs:1111-1158](file:///d:/JProgram/2026/A205自动测试系统/UI/AutoTestPanel.cs#L1111-L1158)

**事实（已 grep 全仓库确认）**：

`RunAllAsync` 的调用点**只有一处** —— `Tests/AutoTest.Tests/Program.cs:145`。生产代码零引用。

引擎在生产中仍被真实使用的只有 3 处：

| 成员 | 生产调用点 | 作用 |
| --- | --- | --- |
| `RegisterTest` | [AutoTestPanel.cs:519](file:///d:/JProgram/2026/A205自动测试系统/UI/AutoTestPanel.cs#L519) | 把测试项注册进引擎 |
| `Clear` | [AutoTestPanel.cs:458](file:///d:/JProgram/2026/A205自动测试系统/UI/AutoTestPanel.cs#L458) | 清空注册表 |
| `LogEmitted` | [AutoTestPanel.cs:110](file:///d:/JProgram/2026/A205自动测试系统/UI/AutoTestPanel.cs#L110) / `:125` | 订阅引擎日志 |

`UnregisterTest`（`:37`）与 `Count`（`:22`）在生产中**无任何调用点**，属纯死代码。

**为什么「调度逻辑双份」不准确** —— 逐行比对两段循环：

| 维度 | 引擎 `RunAllAsync`（`:61-91`） | UI 生产循环（`AutoTestPanel.cs:1114-1124`） |
| --- | --- | --- |
| 迭代对象 | `_items`（`ITestItem` 列表） | `dgvTests.Rows`（DataGridView 行） |
| 单项执行 | **直接 `await item.ExecuteAsync(progress, ct)`** | **委托给 `RunSingleTestAsync(i, isFromRunAll: true)`** |
| 取消检查 | 仅循环**前**一次 `ct.ThrowIfCancellationRequested()` | 循环**前后各一次** `_runCts.IsCancellationRequested` |
| 异常隔离 | 有 —— `catch (Exception)` 记日志后**继续下一项** | **无** —— 异常冒泡出 `RunSingleTestAsync` 的 catch 后，仍继续下一项 |
| 进度回调 | `progress?.Report(prefix)` 文本前缀 | `UpdateProgress(percent, step)` 百分比 + 文字 |
| 批次统计 | 无 | `_progressCompleted / Passed / Failed` 累计 |
| 跳过逻辑 | 无 | 「带内虚假信号」需人工换滤波器 → 标记「需人工操作」并 `return`（`:881-892`） |
| UI 状态还原 | 无 | `TryRestoreRowVisuals` + 按钮 enable/disable + cts 释放 |
| 终态快照 | 无 | `UpdateTestProgress(Aborted/Finished, ...)` |

**结论**：两者**不是同一逻辑的两份拷贝**。引擎是 30 行的通用串行调度器；UI 循环是 45 行的**带 UI 状态管理的业务编排**，两者职责差异很大（UI 侧多了跳过逻辑、批次统计、进度快照、DGV 视觉还原、逐项 cts 生命周期管理）。

**真实的问题**（这才是本条的实质）：

1. **生产调度逻辑零测试覆盖**。`AutoTest.Tests` 的 85 条断言中，唯一覆盖调度语义的是 `TestAutoTestEngine`（`Program.cs:125-155`），它测的是**引擎**，而生产跑的是 **UI 循环**。UI 循环里的这些分支**没有任何测试**：
   - 取消在循环**前**生效（`:1117` break）vs 循环**后**生效（`:1123` break）的差异
   - 「带内虚假信号」被跳过后 `_progressCompleted` 不递增、但 `_progressTotal` 仍含它 → 进度条终态百分比可能不到 100%
   - `_runAllInProgress` / `_progressTimer` 的 finally 清理在异常路径下是否正确复位

2. **「测试对象 ≠ 生产对象」是更危险的形态**。当前 `AutoTest.Tests` 给人「引擎调度已被验证」的错觉，而实际被验证的是一段**生产中不执行的代码**。若将来有人修改引擎的取消/异常语义并依赖测试通过做保障，改动**不会影响生产行为**。

3. **死代码伪装成活跃抽象**。`RegisterTest` / `Clear` / `LogEmitted` 让引擎看起来"在用"，但最核心的 `RunAllAsync` 从未执行。`UnregisterTest` 与 `Count` 则是 100% 死代码。

**建议（三选一，按推荐度排序）**：

| 方案 | 做法 | 收益 | 风险 |
| --- | --- | --- | --- |
| **A（推荐）** | **删除 `AutoTestEngine` 整个类**，把 `TestAutoTestEngine` 的断言迁到 `AutoTestPanel` 的循环语义上（或抽出一个可测的纯函数 `BatchRunner.RunAsync(items, ct)`） | 消除死代码与"测试对象≠生产对象"的错觉；生产路径即被测路径 | 中 —— 需重构 UI 循环为可测单元 |
