## 一、项目概述

### 1.1 项目背景

A205接收模块是一款八通道接收机模块，其每个通道需要输入RF射频信号和IF本振信号方可正常工作，并输出中频信号（模式1/2输出70MHz中频，模式3输出750MHz中频）。为提升测试效率、降低人工操作误差，需开发一套上位机自动测试系统，实现对接收模块的参数配置、工装矩阵通道切换以及测试仪器的自动化控制，完成各项射频指标的自动测量与数据记录。

### 1.2 软件名称

A205自动测试系统

### 1.3 软件定位

本软件为A205接收模块的专用上位机控制程序，主要实现以下核心能力：

- 通过串口向接收模块发送十六进制控制命令，完成工作参数配置
- 通过工装矩阵串口向单片机发送通道切换命令，实现射频信号路径的自动切换
- 通过VISA协议控制信号源、频谱仪、直流电源等测试仪表，完成自动化测试流程
- 自动记录测试数据并生成Excel格式测试报告

### 1.4 适用范围

本软件适用于A205接收模块在常温、高温、低温三种温度区间下的出厂测试与性能验证。

## 三、系统架构设计

### 3.1 整体架构

本软件采用**四层**分层架构设计，自上而下分为界面层（UI Layer）、业务逻辑层（Business Layer）、驱动层（Driver Layer）和传输层（Transport Layer），外加 2 个横切支撑模块：

```
+------------------------------------------------------------------+
|                    界面层 (UI Layer)                               |
|  +------------------+  +--------------------------------------+   |
|  |  接收机控制区     |  |  自动测试区 (独立Tab页)              |   |
|  |  (含工装矩阵控制) |  |  测试项目表格 + 状态显示             |   |
|  |  仪表连接状态显示 |  |  测试进度 + 日志输出                 |   |
|  +------------------+  +--------------------------------------+   |
+------------------------------------------------------------------+
|               业务逻辑层 (Business Layer)                          |
|  +------------------------------------------------------------+  |
|  |  自动测试引擎 (AutoTestEngine) + 测试项目录 (TestCatalog)  |  |
|  |  测试项契约 (ITestItem) + 共用算法/数据 (Shared/)         |  |
|  +------------------------------------------------------------+  |
+------------------------------------------------------------------+
|                驱动层 (Driver Layer)                              |
|  +------------+ +------------+ +----------+ +------------+        |
|  |接收机串口类 | |矩阵串口类  | |信号源类  | |频谱仪/电源类 |        |
|  +------------+ +------------+ +----------+ +------------+        |
+------------------------------------------------------------------+

|  |  IVisaTransport 抽象 → VISA 会话管理 / 超时 / 重试 / 失联   |  |
```

- `Common/TestReportManager.cs` + `Common/ExcelExporter.cs`：结果聚合与 Excel 落盘

### 3.3 设计原则

- **高内聚低耦合**：接收机、工装矩阵、各仪表分别封装为独立类，通过接口或事件进行交互，便于独立调试和排查 Bug
- **可扩展性**：测试项目采用独立类文件管理，新增测试项目只需添加新的测试类并注册到测试引擎，无需修改核心框架
- **可维护性**：串口通信提取公共基类，减少重复代码；命令构建与通信收发分离，便于协议变更时快速调整
- **目录即职责**：一个目录只承载一类职责。`InstrumentControl/` 只放真正与仪表打交道的代码，测试编排、纯算法、纯数据模型各归其位
- **目录即命名空间**：文件夹路径与 C# 命名空间严格一一对应，杜绝"文件位置与命名空间不一致"造成的定位困难

## 四、功能模块详细设计

### 4.1 模块一：接收机控制（含工装矩阵联动）

#### 4.1.1 功能概述

本模块是软件的核心控制模块，集成接收机参数配置和工装矩阵通道切换两大功能。用户在界面上选择参数后，程序同时向接收机串口和工装矩阵串口发送对应的十六进制控制命令。

#### 4.1.2 串口通信协议

根据现有命令样本，接收机串口通信帧格式如下：

| 帧头 | 指令码 | 数据段 | 帧尾 |
|------|--------|--------|------|
| 0D | 1 Byte | 4 Bytes | 0A |

已确认的命令对照（部分）：

| 功能 | 命令示例 | 说明 |
|------|----------|------|
| 模式切换-模式1 | 0D 31 00 00 00 00 0A -> 0D 24 00 00 00 00 0A -> 0D 24 00 00 00 00 0A | 三条命令序列 |
| 模式切换-模式2 | 0D 31 00 00 00 00 0A -> 0D 24 00 00 00 00 0A -> 0D 24 00 00 00 00 0A | 三条命令序列 |
| 模式切换-模式3 | 0D 31 03 00 00 00 0A -> 0D 24 00 00 00 00 0A -> 0D 24 00 00 00 00 0A | 第 1 条数据段不同 |
| 通道选择(1-8) | 0D 11 XX 04 00 00 0A | XX 为通道号 01-08 |

注：工装矩阵串口通信协议与接收机串口类似，具体命令格式待后续确认。

#### 4.1.3 控制参数说明

| 参数类别 | 可选值 | 说明 |
|----------|--------|------|
| 温度区间 | 常温/高温/低温 | 用于标记当前测试环境温度条件 |
| 通道选择 | 通道1~通道8 | 选择当前操作的接收通道，同时联动工装矩阵切换 |
| 模式选择 | Mode1/Mode2/Mode3 | 切换接收模块工作模式 |
| 频段选择 | 按模式差异 | 模式1/2/3 分别对应 18 / 20 / 22 个频点 |
| AGC 衰减控制 | 按测试项定义 | 控制自动增益控制的衰减值 |

#### 4.1.4 通道联动逻辑

当用户在界面上选择某一通道时，程序执行以下联动操作：

```
用户选择通道N
    |
    +---> 接收机串口：发送通道选择命令 0D 11 N 04 00 00 0A
    |
    +---> 工装矩阵串口：发送矩阵通道切换命令（切换射频信号路径至通道N）
```

**实现约定（V1.0 遗留待确认项已定）**：

- 通道下拉框**只切换矩阵**，不隐式发送接收机命令
- 模式 RadioButton 切换时**隐式联动**：刷新频段下拉框 → 同步频谱仪中心频率/Span → 调整 RF/LO 输出功率（RF：Mode1/3 = −20 dBm，Mode2 = −10 dBm；LO：三种模式均 3 dBm）
- `btnModeSet` 发送顺序：通道帧 → 100 ms 间隔 → 模式序列
- 接收机通道选择帧参数字节 P 与模式相关（Mode1=0x03、Mode2=0x02、Mode3=0x04），**与通道号无关**

#### 4.1.5 类设计

**ReceiverSerialPort.cs（接收机串口通信类）**

- 职责：管理接收机串口的连接、断开、数据收发
- 核心方法：`Open()`、`Close()`、`SendTemperatureCommand()`、`SendBandCommand()`、`SendChannelThenModeCommand()`
- 继承自 `SerialPortBase` 公共基类

**MatrixSerialPort.cs（工装矩阵串口通信类）**

- 职责：管理工装矩阵串口的连接、断开、数据收发
- 实现 `IChannelSwitcher` 接口
- **当前为桩实现**：协议未到位，`Connect`/`Disconnect`/`SwitchChannel` 仅记日志，不真正打开串口，`IsConnected` 恒为 false

### 4.3 模块三：自动测试

#### 4.3.1 功能概述

自动测试模块放置在独立的 Tab 页中，以 DataGridView 表格形式列出各测试项目。用户点击行内"运行"按钮后，程序自动执行完整的测试流程：配置仪表参数 → 等待稳定 → 采集数据 → 判定结果 → 记录数据。

#### 4.3.2 测试流程通用框架

每个测试项目的执行流程遵循统一框架：

1. **前置检查**
   - 检查串口连接状态（接收机 + 工装矩阵）
   - 检查仪表连接状态（信号源 x2 + 频谱仪 + 电源）
   - 检查当前通道、模式、温度区间参数是否已配置
   - 通过 `ResourceSnapshotLogic.EvaluateReadiness` 一次性快照判定，**避免多步读取间状态被异步改动**
2. **模式 × 频点双层遍历**
   - 按 `ModeBandTable.GetBands(mode)` 取当前模式的全部频点
   - 通过频段显示名反查频段信息（依赖 `"频段" + Math.Round(freqMHz)` 命名契约）
3. **仪表参数配置**
   - 配置 RF 信号源（频率、功率）
   - 配置 LO 信号源（频率按 `LoFrequencyRule` 由 RF 推算、功率、开关）
   - 配置频谱仪（中心频率、Span、RBW 等）
   - 发送接收机频段命令 / 衰减命令
4. **执行测量**
   - 等待信号稳定（延时按模式区分，注释写明量化依据）
   - 从频谱仪读取测量数据
5. **结果判定**
   - 将测量值与预设指标上下限对比
   - 判定 Pass / Fail
6. **数据记录**
   - 记录测试时间、通道号、温度区间、频段、模式
   - 记录测试项目名称、测量值、判定结果
   - 写入 `TestReportManager` 待导出批次
7. **硬件复位（finally 兜底）**
   - 每条命令**单独 try**，确保前一条抛异常不影响后续复位
   - 关闭 RF/LO 输出、停止扫频、恢复频谱仪参考电平、衰减复位 0 dB
8. **异常处理**
   - 捕获异常写日志，不中断整批测试；已采集数据不丢失

#### 4.3.3 测试项目扩展机制

测试项目采用独立类文件管理，每个测试项目实现统一的接口：

```csharp
public interface ITestItem
{
    string TestName { get; }                    // 测试项目名称（如 "线性最大增益"）
    string Unit { get; }                         // 测量单位（dB / MHz 等）
    double? LowerLimit { get; }                 // 判据下限（包含），null 表示不设下限
    double? UpperLimit { get; }                 // 判据上限（包含），null 表示不设上限
    Task<TestResult> ExecuteAsync(
        IProgress<string> progress,             // 进度上报通道
        CancellationToken ct);                  // 取消令牌
}
```

新增测试项目时，只需：

1. 在 `InstrumentControl/TestItems/` 中创建新的测试类文件
2. 实现 `ITestItem` 接口
3. 在 `AutoTest/TestCatalog.cs` 中注册

**UI 层无需任何改动** —— UI 持有的类型是 `ITestItem` 而非任何具体测试类。

#### 4.3.5 增益一致性共用算法

两个「通道间增益不一致性」测试项共用 `GainConsistencyCalculator`，保证判定口径完全一致：

- **输出值 = 最差值**：距等效增益规格边界最近的那个值，距离统一用 `min(|v−lower|, |v−upper|)` 计算（规格区间内外都成立）
- **Pass/Fail = 极差**：`max − min`，≤ 1 dB 判 Pass
- 改算法只改一处

## 七、通信架构设计

### 7.1 串口通信

#### 7.1.1 公共基类 SerialPortBase

封装串口通用操作，供接收机和工装矩阵串口类继承：

- 串口参数配置（COM 口、波特率、数据位、停止位、校验位）
- 连接/断开管理
- 数据发送（支持字节数组和十六进制字符串）
- 数据接收事件（`DataReceived`）
- 通信日志记录

#### 7.1.2 通信方式

**已定**：串口通信采用**同步发送 + 日志记录**模式。接收机协议为"只发不收"（无响应报文），无需异步回读。

VISA 通信为**同步请求-响应**模式（`QueryString` 内部含超时与重试）。

### 7.2 VISA 通信

- 基于 NI-VISA 驱动库，通过 `Ivi.Visa` / `NationalInstruments.Visa` 命名空间进行通信
- 采用 SCPI（Standard Commands for Programmable Instruments）标准命令集控制仪表
- 每个仪表类封装对应的 SCPI 命令集合

**传输层抽象**：

```csharp
public interface IVisaTransport : IDisposable
{
    string Address { get; }
    bool IsOpen { get; }
    int TimeoutMilliseconds { get; set; }
    void Open();
    void Write(string data);
    string ReadString();
}
```

| 实现 | 位置 | 用途 |
|------|------|------|
| `NationalInstrumentsVisaTransport` | 生产代码 | 真实 NI VISA 25.0 |
| `FakeVisaInstrument` | `Tests/*/FakeVisaInstrument.cs` | 单元测试替身 |

`VisaBaseInstrument` 只依赖接口，不直接引用 `NationalInstruments.Visa` 的类型。测试时通过 `SetTransport()` 注入伪传输，使得**整个仪表调用链可以在没有硬件的环境下测试**。

## 八、异常处理与容错设计

### 8.1 串口通信异常

| 异常场景 | 处理方式 |
|----------|----------|
| 串口打开失败 | 弹出提示框，提示用户检查 COM 口和连接 |
| 串口意外断开 | 自动检测并更新连接状态指示，弹出告警提示 |
| 命令发送超时 | 重试机制（最多 3 次），超时后提示用户 |

### 8.2 仪表通信异常

| 异常场景 | 处理方式 |
|----------|----------|
| VISA 资源未找到 | 提示用户检查仪表连接和 VISA 地址 |
| 仪表无响应 | **瞬态错误**（超时/系统错误/IO/连接丢失）→ 3 次重试 + 指数退避（100/200/400 ms）；**非瞬态错误** → 立即标记失联并抛出，触发 `ConnectionChanged(false)` 让 UI 状态灯变红 |
| 测量值异常 | 数据合理性校验，异常值标记并记录 |

> **瞬态判定依据**：按 VISA 规范 `HResult` 常量比对（`VI_ERROR_TMO = -1073807339` 等）。
> **失联标记的意义**：避免线缆掉了但 `IsConnected` 字段仍卡 true，导致「一键连接」走"已连接"快路径跳过重连，直到下次发命令才报错。

### 8.3 测试流程异常

- 测试前自动检查所有依赖（串口、仪表连接状态），未就绪时禁止启动测试
- 测试过程中发生异常时，捕获并记录异常信息，不中断整批测试
- 已完成的测试数据不因后续异常而丢失
- **硬件状态兜底**：所有 `finally` 块中每条复位命令单独 `try`，确保仪表不会停留在异常状态污染后续测试项

### 8.4 无真机演示（测试工程）

通过 `FakeVisaInstrument` 测试桩，在无真实仪表的环境下验证整条仪表调用链：

- `Tests/AutoTest.Tests` 与 `Tests/Instrument.Tests` 各持有一份 `FakeVisaInstrument`（同源实现）
- 测试工程通过给 `VisaBaseInstrument.DefaultTransportFactory` 注入伪传输，使生产类（`SignalGenerator` / `SpectrumAnalyzer`）走假传输
- **测试工程不引用 `NationalInstruments.Visa.dll`**，因此 `Program.Main` 中注册的 `NationalInstrumentsVisaTransport` 只在生产工程生效

## 十一、目录整理专项（V2.0 新增）

### 11.1 动机

早期 `InstrumentControl/` 目录同时承载了四类互不相干的内容：

| 类别 | 文件 |
|------|------|
| 真·仪表驱动 | `VisaBaseInstrument`、`NationalInstrumentsVisaTransport`、`SignalGenerator`、`SignalGeneratorLO`、`SpectrumAnalyzer`、`ODP3063` |
| 测试编排 | `AutoTestEngine`、`TestCatalog`、`ITestItem` |
| 纯数据模型 | `TestResult` |
| 纯算法 / 纯数据（不碰硬件） | `LoFrequencyRule`、`GainResultRepository`、`GainConsistencyCalculator`、`ResourceSnapshotLogic` |

目录名与实际内容不符，读者难以快速判断"改这个文件会影响哪一层"。

### 11.2 迁移清单

| # | 原路径 | 新路径 | 新命名空间 |
|---|--------|--------|-----------|
| 1 | `InstrumentControl/TestResult.cs` | `Models/TestResult.cs` | `A205AutoTestSystem.Models` |
| 2 | `InstrumentControl/LoFrequencyRule.cs` | `AutoTest/Shared/LoFrequencyRule.cs` | `A205AutoTestSystem.AutoTest.Shared` |
| 3 | `InstrumentControl/GainResultRepository.cs` | `AutoTest/Shared/GainResultRepository.cs` | `A205AutoTestSystem.AutoTest.Shared` |
| 4 | `InstrumentControl/TestItems/GainConsistencyCalculator.cs` | `AutoTest/Shared/GainConsistencyCalculator.cs` | `A205AutoTestSystem.AutoTest.Shared` |

### 11.3 整理后的收益

- `InstrumentControl/` 最终**只剩 6 个真正发指令的仪表驱动**，目录名与内容完全对应
- 测试编排（`AutoTest/`）、纯算法（`AutoTest/Shared/`）、纯数据模型（`Models/`）各自独立
- 12 个测试项**位置全部不变**，`InstrumentControl/TestItems/` 仍是一份干净的测试项清单

### 11.4 命名空间变更说明

命名空间随目录同步调整，理由：

1. **命名空间是编译期概念**：C# 中同程序集内的类型引用编译为 metadata token 而非字符串，改命名空间**不产生任何 IL 差异**，运行时行为零差异
2. **项目既有约定**：全部源文件的命名空间与文件夹路径一一对应，若保留旧命名空间将新增 8 处"位置与命名空间不一致"
3. **无反射依赖**：全项目 `typeof()` / `GetType()` / `Assembly.` / `Activator` 扫描确认，无按字符串拼装命名空间的用法

**唯一实质风险**：C# 的"外层命名空间可见性"。原位于 `InstrumentControl.TestItems` 下的 12 个测试项未写 `using` 即可直接访问 `SignalGenerator` / `TestResult`；改名后需显式补 `using`。该问题由编译器逐条列出，**不可能遗漏**。
